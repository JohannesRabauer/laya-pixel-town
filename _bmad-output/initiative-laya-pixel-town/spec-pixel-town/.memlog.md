topic: Pixel Town: Laya-driven town simulation web app
updated: 2026-10-04T15:00
---


- (direction) Fast-tracked spec; user wants to see a running version soon. Inputs: ux-pixel-town DESIGN.md + EXPERIENCE.md drafts (adopted as companions) and mocks.
- (decision) Why: vision to realize. A visual showcase of Laya making many typed decisions quickly; viewer is a god-observer, no player/game.
- (capability) CAP-1 Start screen: set population (10-300), decision interval, seed, Laya address; Start only enabled when Laya is reachable.
- (capability) CAP-2 Simulation: about 100 people with five needs (hunger, energy, social, fun, money) act in a top-down pixel town; each tick every due person gets one Laya choice question over seven activities (sleep, eat, work, socialize, relax, shop, wander); chosen activity drives movement.
- (capability) CAP-3 Batching: all decisions due in a tick go to Laya as one POST /v1/systemone/batch call.
- (capability) CAP-4 Observe controls: pause/resume, step one tick, speed 1x/2x/5x, day/night with night tint, hover label, click-to-select person.
- (capability) CAP-5 Inspector: selected person's needs, current activity, last decision (exact state text, per-option probabilities, chosen option, latency, answer_confidence), last-10 history.
- (capability) CAP-6 Metrics: top bar shows decisions/s, batch size, last batch ms; Laya failure mid-run keeps people in current activity and shows a message.
- (constraint) Simulation runs server-side in Java, one batch call per tick; browser only renders (canvas, nearest-neighbour). Reason: batch speed is the showcase.
- (constraint) Laya via laya-serve at configurable base URL, default http://localhost:8002 (running locally in Docker, Laya 0.3.26). Batch limit 64 states per call: larger ticks must be chunked. Choice question; labels returned verbatim; gate abstain on answer_confidence, not confidence.
- (constraint) langchain4j-typesafe 1.21.0-beta31 has no batch call, so batch goes over plain HTTP (JDK HttpClient + Jackson); LangChain4j TypeSafeDecisionModel is optional for single-decision path.
- (constraint) Stack: Java 17+ (local JDK 18), Maven 3.9, Spring Boot, static HTML/JS frontend, server pushes state to browser (SSE or WebSocket). No DB, no accounts, no persistence.
- (constraint) State text front-loaded and short (Laya reads 512 tokens).
- (decision) Non-goals: player character, score, win state, building or ordering people, saved games, accounts, mobile layout, multiplayer, persistence.
- (decision) Success: with laya-serve running, Start gives a moving town of 100 people; clicking a person shows a real Laya decision card; batch tile shows real ms; pausing and stepping works; night makes most people sleep.
- (assumption) Per-person decision cadence: each person re-decides when their activity finishes or every N sim-seconds, whichever first. Open.
- (assumption) Needs drift over time (hunger rises, energy falls) and activities restore them; buildings typed home/work/restaurant/shop/park. Tuning to be found while prototyping.
- (question) Use LangChain4j TypeSafeDecisionModel anywhere, or plain HTTP only? User asked for LangChain4j; batch forces plain HTTP.
- (event) Pass 1 coherence and Pass 2 preservation self-validated; UX spines adopted as companions rather than absorbed.
- (constraint) Laya choice question field is 'instructions' (not 'question'); 422 otherwise. Verified against laya-serve 0.3.26 on 2026-10-04.
- (decision) Built and ran v0.1: Spring Boot 3.3 + static canvas front end on port 8765; plain JDK HttpClient to /v1/systemone/batch; no LangChain4j in the app (batch is not supported by langchain4j-typesafe 1.21.0-beta31).
- (constraint) Measured: CPU laya-serve ~0.7 s/state (64 states ~46 s); CUDA (RTX 3060, torch 2.14 cu130) 64 states ~2.7 s, ~70 ms per small warm batch. GPU contention (Ollama in another project) stalls CUDA completely. Laya CUDA wheels: torch 2.14 exists on cu130 index, not cu128.
- (constraint) State text must name needs only. Including the current activity ('Right now X is relaxing') or daytime phrases made Laya answer 'relax' at 0.99 for everyone. Time mentioned only at night. Needs-only wording scored 6/10 on a hand-built check.
- (decision) Decision flow is a rolling queue, not a fixed per-tick batch: due people (oldest first, max 64) are sent as soon as the previous call returns; people keep their activity until answered. Metrics are real wall-clock.
- (decision) Deployment: single 'docker compose up --build' builds Laya from upstream commit 2e4d9c8 (CUDA by default, compose.cpu.yaml override) and the app; app on 8765, Laya on 8003 (host).
- (decision) Abstention (not-sure state) and keyboard-only person selection are not built in v0.1.
- (event) Spec re-derived after v0.1 build: CAP-3 reworded to rolling batches, constraints updated, stack.md corrected.
