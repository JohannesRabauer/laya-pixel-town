- (decision) Backend: HTTP client to laya-serve /v1/systemone first; in-process ONNX Runtime backend deferred to a later version
- (decision) Stakes: public OSS library published to Maven Central; needs polished API, docs, semver
- (decision) Baseline Java 17 (records, sealed types, java.net.http)
- (decision) Working mode: fast path with [ASSUMPTION] tags
- (decision) Targets: one client for both laya-serve and hosted Jev API via the shared Jev-compatible protocol; configurable base URL + key, differences handled as quirks
- (decision) Integrations in scope: Spring Boot starter, LangChain4j, Spring AI (in addition to core client)
- (decision) Question API style: fluent builders only (no annotated records, no raw-map API chosen)
- (decision) Maven coordinates dev.rabauer:laya-java-client (user override of proposed software.xdev)
- (event) Research digest: laya-serve mirrors TypeSafe POST /v1/systemone (+/batch, /health); Laya returns superset of Jev response; LAYA_JEV_STRICT trims to Jev contract; no Java SDK exists for Jev or Laya
- (event) Research: jevai.org decide() shorthand is a third-party/marketing wrapper, not the official TypeSafe SDK (system_one + Choice/Noul/Score builders, RetryPolicy, typed exceptions); model the Java API on the official SDK
- (assumption) v1 scope = core client + Spring Boot starter; LangChain4j and Spring AI adapters follow in 1.x (pushback on three integrations in v1)
- (assumption) Retries: opt-in policy modelled on TypeSafe RetryPolicy; default retries only 429/503 honoring Retry-After, since repeating inference is costly (laya-client TS never retries)
- (assumption) Confidence: expose both confidence and answerConfidence; gating helpers default to answerConfidence; score exposes argmax level label, not rounded expected value
- (assumption) dev.rabauer namespace is (or can be) verified on Maven Central
- (decision) Parked: annotated-record decide(Class) (Laya decide(schema) analogue) - not chosen for v1, kept for vision
- (decision) Rejected in-process ONNX pivot: Laya stays a separate Docker container (laya-serve); Java talks HTTP only
- (event) Prior art found (corrects brief): org.springaicommunity:typesafe-java-sdk 0.4.0 (+starter, Spring AI judge/guardrail/RAG; has a Using-Laya doc page) and dev.langchain4j:langchain4j-typesafe 1.21.0-beta31 (DecisionModel API, any /v1/systemone server via baseUrl). Brief claim 'no Java client exists' is false
- (event) Verified 2026-10-04 against laya-serve (Docker, commit 2e4d9c8, english, CPU): both clients work unchanged for noul/choice/score. Both send only model/state/questions and drop answer_confidence, abstention, routing, usage.truncated; cannot send lang/min_confidence/max_len; neither uses /v1/systemone/batch (Spring fans out client-side; Laya serves one forward pass at a time). Both expose entropy confidence, which Laya docs say not to gate on
- (override) Reframed product: from standalone dev.rabauer:laya-java-client to Laya support for the JVM via upstream contributions (spring-ai-typesafe + langchain4j). Reason: both existing clients already work with laya-serve; the gap is Laya-only fields, which fits their extension points
- (decision) Standalone client kept only as fallback if both upstream projects decline; earlier v1 scope (own builders, own Spring Boot starter, own LC4j/Spring AI adapters) dropped
- (event) LangChain4j DecisionRequestParameters and DecisionResponseMetadata are documented as extensible by provider integrations (self-typed builders) -> natural home for a Laya provider module
